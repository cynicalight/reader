# Reader 聊天改进候选实测

日期：2026-10-07（北京时间）。基线：`main` 的 `7a4d895`。CLI：`codex-cli 0.160.1`。实际模型：`gpt-6.1-sol`；effort：medium。关联问题：[GitHub issue #4](https://github.com/cynicalight/reader/issues/4)。本次只测试候选，不发布产品实现。

## 结论

全部 **36 次真实生成调用均通过 Reader HTTP 聊天入口**，正常保存用户问题和真实回答、读取历史、记录每轮用量。两组配对场景的协议及保存检查全部通过，18 次指定预算事实检查也通过。

- 摘录去重＋完整消息截断候选：12 轮累计输入比现有实现减少 **19.1%**，缓存比例未改善。
- 同 thread 连续追加候选：12 轮整体输入缓存比例 **80.13%**，恒定摘录组 **82.29%**，切换来源及重建组 **77.96%**。这次已经过 Reader 保存／读取链路，区别于此前仅有原生 CLI 对照。
- 单条历史来源超过预算时，去重候选仍丢失原始来源，确定性测试失败。因此候选不具备直接发布条件。

本次没有额外实际调用、采集丢失或付费重试。记录先落盘再断言。实验产品改动最终恢复；提交仅保留研究报告、原始记录和复现材料。

## 方法和条件

在独立临时 SQLite 书库注册 6 个合成文档。真实 HTTP server 绑定 `127.0.0.1`，使用认证请求调用 `/api/documents/{id}/chat`，再读取 `/messages` 和 `/chat-usage`。不使用真实书库，不发送用户文档或图片；不手工写入回答或已完成历史，不启用 API fallback。

三个条件各在两个场景中执行六轮，合计 36 次：

1. **baseline**：当前实现，随机隔离目录、每轮新 App Server / ephemeral thread、原样历史拼接。
2. **dedup**：按 source hash 标记引用；选入的历史摘录按初次出现顺序只发送一次；按完整消息保留历史，超过字节预算即停止选择，不切 UTF-8 字符。仍每轮使用新随机目录、新 App Server / thread。
3. **session**：使用同一个去重首轮提示，正常读取已保存消息；专用空目录中的长驻 App Server / ephemeral thread 追加新问题和首次出现的新摘录。每轮核对 provider 预期历史与 SQLite 实际保存历史，不一致则重建。指标读取 `tokenUsage.last`。

第二组第 6 轮主动关闭 session 候选的 Codex 子进程，再通过 Reader 已保存历史构造完整提示并新建 thread。它是 provider 进程重建测试，**不是 Electron / Go 服务整体重启，也不是 thread/resume 持久会话恢复**。

第 1 组每轮顺序是 baseline → dedup → session；第 2 组反转为 session → dedup → baseline。对照使用同一来源和问题，各条件分别获得模型真实回答；不复制其他组的回答。每组有不同实验标识，记录在 JSONL 中。缓存初始状态未知，交错执行也不能消除全部共享缓存和服务路由影响。

协议依据：[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server) 支持在同 thread 追加 turn，Reader 仍承担自身保存及生命周期契约。实验复用适配器仅在临时测试补丁中注册，不是产品默认行为。

## 场景和事实检查

**场景 1：恒定长摘录。** 在此前 11,101 字节合成材料前加入实验标识及事实“甲队预算730元”。六轮分别问文章结论、缓存输入计数、甲队预算、历史截断、费用区分和保持前缀稳定的两个做法。第 3 轮必须包含阿拉伯数字730。

**场景 2：切换来源、空上下文、子进程重建。**

| 轮次 | 当前摘录 | 问题与检查 |
|---|---|---|
| 1 | 长来源 A | 甲队预算，核对730 |
| 2 | A | 解释缓存读取计入输入总量 |
| 3 | A | 再次核对甲队预算730 |
| 4 | 新来源 B | 乙队预算，核对910；B不重复甲队预算 |
| 5 | 空 | 根据已保存历史核对甲队730、乙队910 |
| 6 | 空 | 差额180，并说明730、910；session条件在请求前关闭子进程 |

每个场景×条件最终保存12条消息、6次完成调用。36轮均验证 SSE done、无 error/fallback、实际返回模型、保存数量、用量数量、本轮问题及前一轮真实回答出现在 Reader 构造的提示中。session 后续转发只包含新增材料与本轮问题；已有对话由 provider thread 保留。首次／重建请求转发完整的 Reader 历史提示。

18轮有指定数字检查，全部通过。其余问题主要验证成功保存及协议，**没有执行完整语义质量评估**；数字包含检查不等于一般阅读理解评估。

## 汇总结果

缓存读取包含于输入，不重复加总。

| 场景 | 条件 | 输入 | 输出 | 缓存读取 | 缓存读取/输入 | 命中轮数 | 平均HTTP耗时 |
|---|---|---:|---:|---:|---:|---:|---:|
| 恒定摘录 | baseline | 121,824 | 240 | 34,944 | 28.68% | 3/6 | 12.66秒 |
| 恒定摘录 | dedup | 94,848 | 224 | 23,296 | 24.56% | 2/6 | 10.24秒 |
| 恒定摘录 | session | 95,039 | 212 | 78,208 | 82.29% | 5/6 | 4.16秒 |
| 切换／重建 | baseline | 112,909 | 97 | 34,944 | 30.95% | 3/6 | 11.04秒 |
| 切换／重建 | dedup | 94,982 | 92 | 23,296 | 24.53% | 2/6 | 10.48秒 |
| 切换／重建 | session | 94,899 | 91 | 73,984 | 77.96% | 5/6 | 4.66秒 |

| 条件，12轮 | 输入 | 输出 | 缓存读取 | 缓存读取/输入 | 平均HTTP耗时 |
|---|---:|---:|---:|---:|---:|
| baseline | 234,733 | 337 | 69,888 | 29.77% | 11.85秒 |
| dedup | 189,830 | 316 | 46,592 | 24.54% | 10.36秒 |
| session | 189,938 | 303 | 152,192 | 80.13% | 4.41秒 |

dedup 比 baseline 少44,903输入tokens，约19.1%；恒定摘录组减少22.1%，切换组减少15.9%。session同时改变进程生命周期、消息边界、隐式历史保留和新增摘录发送方式，不能把缓存与时间改善全部归因于单一因素。session正常保留整个实验thread，超过最近8条消息的部分不会像baseline那样滚动移除；这也是两种方案的语义差异。

36次调用合计：输入 **614,501**、输出 **956**、总量 **615,457**；缓存读取 **268,672** 已包含于输入。这是服务报告用量，不是费用／订阅额度折算。模拟CLI和纯离线测试不包含在这个实际调用汇总内。

## 边界测试：通过项和失败项

### 确定性结构反馈

`READER_STRUCTURE_MODE=baseline ... -run '^TestImprovementStructure$'` 失败：同一完整来源出现3次，要求仅1次。切到dedup条件后同一测试通过。该路径调用真实chat handler、保存用户和模拟回答；没有真实模型调用。

36轮真实数据中，baseline构造提示共有5个截断产生的U+FFFD：第1组3个，第2组2个。dedup和session组构造提示没有U+FFFD。应用提示在JSON中已规范化，不能用解码后的长度直接等同Go原始字节数。

### 模拟生命周期及记账

以下测试及对应 `go test -race` 通过：

- `TestProtoCancellationDropsSession`：模拟CLI输出partial后取消，实验适配器杀死子进程并丢弃不确定会话。它是适配器／子进程测试，不是实际网络中断或HTTP客户端断连测试；启动握手阶段取消未验证。
- `TestProtoSaveFailureRebuildsFromSQLite`：Reader真实chat handler，模拟CLI返回答案；SQLite触发器使assistant保存失败，SSE返回error而不是done；恢复数据库写入后，下一轮发现持久历史不一致、新建thread。最终只保存两条用户消息和第二轮assistant，未保存失败回答。
- `TestPrototypeLastUsageSchema`：last单轮字段隔离。真实session数据另外逐字段核对持久用量等于last、同thread累加等于total；重建后以新thread重新核对，两个session测试文档各记录6次调用，合计12次，不重复累计旧total。

### 尚未解决：超长来源保留

`TestImprovementOversizeHistoryEvidence` **失败**：一条历史来源约36,000字节，尾部包含独有事实“维修费用471元”，下一轮当前摘录为空。候选为了预算直接拒绝整条user消息，结果保留短回答却丢掉原始来源。它没有解决“预算约束下如何保留可追溯证据”，完整消息边界也不等于完整问答对边界。

该失败不影响上述36轮受限正常场景通过，但阻止把候选认定为通用正确的正式方案。实验source注册也应以真正发送的来源为准，不能仅扫描所有持久消息并把遗漏的来源标记为已发送。

## 下一步实现要求

1. 分离对话文本预算和来源注册，明确超过预算的来源是检索补充、完整保留还是显式不可用；不要静默删来源后仍声称可依据原文回答。保留完整问答对，并测试来源切换及引用可解析。
2. 再把session作为正式服务内模块实现，处理逐文档隔离、文档删除、配置／effort变更、图片、应用退出、启动阶段取消、失败重建及全应用重启。此次只覆盖合成文本、一个活跃会话和固定模型；测试适配器固定medium，没有验证动态模型目录／配置切换。
3. 保持现有stream契约：增量输出、provider成功后保存、不在可见partial后补fallback。指标使用每轮last或可靠差额；若引入工具调用／内部重试，还需确认turn内多次模型请求的统计语义。
4. 在多个独立对话、不同长度／不同类型资料中复测；不设置“每轮必须缓存命中”的不可靠验收条件。
