# 单 thread 翻译速度实测

日期：2026-10-08（Asia/Shanghai）。Codex CLI 0.160.1，Go 1.25.4，macOS arm64。

以下为此前单 worker 方案的历史测量。当前实现已改为 3 个 worker 各自复用会话；这些结果不能作为当前实现的测速结论，`TestLiveTranslationThreadSpeed` 仍比较历史的独立并行与单会话串行两种方案。

后续接近默认 10,000 字符批次的两轮复测见 [大批次报告](./full-batch.md)。本文保留最初的小批次测量，不将其当作大批次性能结论。

## 方法与边界

使用 `TestLiveTranslationThreadSpeed` 的原创英文资料，三个批次，每批两段，分别为 1,372、1,418、1,444 个 Unicode 字符。两组都使用 `gpt-5.6-luna`、`low`、Reader 当前系统提示词和翻译 JSONL 提示词，以及相同的段落 ID、原文哈希、句子覆盖校验器。

- 基线：三个独立 App Server 进程／thread 同时翻译。
- 新方案：一个 App Server 进程／thread，三个连续 turn 顺序翻译，保留历史。
- 两轮采用相反执行顺序；每轮六次真实模型调用，共十二次。没有人为清除服务端缓存。
- 测量覆盖真实 CLI 协议、模型流式生成和段落校验，不包含前端渲染、PDF 提取、SQLite 保存或备用提供者切换；这些路径由自动化测试单独验证。基线直接走相同 Codex 会话实现，不额外测量旧适配器的模型目录查询。
- 每批比生产默认 10,000 字符小；结果不能推广到整篇论文或长会话。没有人工审核中文翻译语义质量。
- 原始逐批指标保存在 [run-1.json](./run-1.json)、[run-2.json](./run-2.json)。只保存时间和 token 指标，没有用户文档或凭据。

## 结果

| 轮次 | 独立 thread 并发总耗时 | 共享 thread 串行总耗时 | 独立组有效段落 | 共享组有效段落 |
|---|---:|---:|---:|---:|
| 1：先并发，再共享 | 22.709 秒 | 52.540 秒 | 5/6 | 6/6 |
| 2：先共享，再并发 | 21.851 秒 | 51.156 秒 | 6/6 | 6/6 |

第 1 轮独立组第 3 批没有得到两条完整有效记录，测试因此返回失败；已经有效的五段不能视为完整翻译。第 2 轮两组均完成全部六段，速度测试通过。

第 2 轮的逐批时间：

| 模式／批次 | initialize | thread/start | 首条文本 delta | 首段有效译文 | 本批完成 |
|---|---:|---:|---:|---:|---:|
| 共享 1 | 0.057 秒 | 0.098 秒 | 10.041 秒 | 16.213 秒 | 22.546 秒 |
| 共享 2 | 无重复调用 | 无重复调用 | 1.638 秒 | 7.852 秒 | 14.436 秒 |
| 共享 3 | 无重复调用 | 无重复调用 | 0.967 秒 | 7.492 秒 | 14.168 秒 |
| 独立 1 | 0.079 秒 | 0.232 秒 | 9.414 秒 | 10.902 秒 | 12.228 秒 |
| 独立 2 | 0.078 秒 | 0.235 秒 | 9.000 秒 | 15.254 秒 | 21.837 秒 |
| 独立 3 | 0.079 秒 | 0.232 秒 | 8.658 秒 | 10.528 秒 | 11.973 秒 |

首条文本、首段和本批完成时间从本批生成开始计时，包含初始化／thread 创建（发生时）；不是从整篇任务开始计时。进程 spawn 约 1–2 毫秒，进程真正就绪的等待包含在 initialize 中。RPC 时间是客户端发出请求到收到响应的经过时间，不是服务端内部操作剖析。

因此，共享第 2 批实际是在整篇开始约 24.18 秒后输出首条文本，第 3 批约 37.95 秒后输出；不能把逐批的 1–2 秒误称为后续所有段落在任务开始 1–2 秒内可见。

两轮共享会话第 2、3 批均报告 11,008、13,056 个缓存输入 tokens；第 2 轮对应输入 13,525、15,149 tokens。第 2 轮独立组也有两批报告 9,984 个缓存输入 tokens，说明新 thread 同样可能命中服务端前缀缓存。不能把 thread 复用当作缓存命中的充分或必要条件。

第一批原文只有约 1,400 个字符，实际输入约 11,900 tokens。这说明附加输入占有显著空间；本实验没有捕获完整模型请求，不能把差额全部归因于 skills 或工具定义。共享输入增长反映历史进入后续轮次。

## 可支持的结论

这两轮小样本里，共享 thread 显著降低后续轮次开始输出前的等待，并得到实际缓存复用；主要等待并不在 thread/start，后者只有约 0.10–0.35 秒。共享串行组总耗时约为并发组的 2.3 倍，不能声称整篇翻译提速。用户要求的串行共享设计仍保留，模型固定 Luna low。

缓存命中、服务端路由和输出速度可能波动。两轮测试不是性能分布，也不证明长 PDF 翻译质量、长会话压缩行为或重启恢复同一个 thread。

## 重跑

在仓库根目录：

```sh
cd apps/server
READER_TEST_TRANSLATION_SPEED=1 \
READER_TRANSLATION_SPEED_OUTPUT=/tmp/reader-translation-speed.json \
go test ./internal/reader -run '^TestLiveTranslationThreadSpeed$' -count=1 -v
```

反转顺序时增加 `READER_TRANSLATION_SPEED_REVERSE=1`。这些命令会发起真实模型调用，普通 `pnpm test` 默认跳过。

## 实现验证

- `pnpm typecheck`：通过。
- `pnpm build`：通过。
- `pnpm test`：Go 全套通过；Vitest 270 通过、3 跳过，1 个 Windows proxy 测试失败。该失败在未修改的 main 上单独复现，为 `PowerShell unavailable`，与本次翻译改动无关。
- `go test -race ./internal/reader -run 'TestTranslation|TestCodexChat' -count=1`：通过，覆盖单进程／单 thread、多 turn、Luna low、用量差分、取消清理、失败重试保留已完成段落，以及聊天模型不被覆盖。

人工验证可在本工作树运行 `pnpm dev`，打开终端输出的带 token 地址。使用已验证的 Codex 主 Agent，导入测试 PDF，观察译文按阅读顺序逐段保存；取消或退出后重新启动，确认已完成段落保留。临时 thread 只在一次翻译运行中复用，重启或重试会新建。
