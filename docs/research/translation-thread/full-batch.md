# 接近默认批次大小的翻译耗时复测

日期：2026-10-08（Asia/Shanghai）。运行 Codex CLI 0.160.1；被测正文实现为 `ccf1050`，测试入口基于 `2d48893` 并增加样本大小参数。

## 条件

对照 main 的三个独立 thread 并发调度方式，与当前分支的一个 thread 串行复用方式。两组固定使用 `gpt-5.6-luna / low`，排除不同模型和 Effort 的影响。

每轮同样的三个批次，分别 10,296、10,641、10,836 个 Unicode 字符，共 31,773 字符；每批 15 段，共 45 段。样本为既有原创英文资料的带编号重复段落，适合受控比较，不能代表真实论文的复杂度或翻译质量。

第一轮先并发后共享，第二轮先共享后并发，共 12 次真实模型调用。每次使用 Reader 的系统提示词、翻译提示词、JSONL 解码及段落 ID／原文哈希／原文句子覆盖校验。

测试直接调用真实 Codex 适配器；对照组模拟 main 的调度方式，没有启动 main 完整 HTTP 服务，也不使用用户在 main 中选择的其他模型。计时不包含 PDF 解析、模型目录查询、SQLite 保存、前端渲染和备用 API。因此这是同模型的 Codex 翻译路径对照，不是完整应用端到端基准。

没有人为清空服务端缓存，没有捕获服务端排队或内部 prefill 耗时，没有人工审核译文语义。

## 完成时间

| 轮次／顺序 | 三独立 thread 并发 | 当前共享 thread 串行 | 当前相对并发 | 校验 |
|---|---:|---:|---|---|
| 1：并发 → 共享 | 108.411 秒 | 69.729 秒 | 少 38.682 秒，缩短 35.68% | 两组均 45/45 |
| 2：共享 → 并发 | 103.958 秒 | 299.267 秒 | 多 195.309 秒，耗时 2.879 倍 | 两组均 45/45 |

两轮真实测试均通过。第一轮不能独立作为稳定提速证据；反向复测没有重复其全文耗时收益。两轮样本不足以描述服务端性能分布，不能宣称稳定快 35.7%，也不能据此宣称生产中固定慢 2.879 倍。

共享会话后续轮次的首条输出为 1.245–2.061 秒，独立请求为 8.706–10.752 秒；这是两轮中较一致的观察。共享组每轮生成速度却波动很大，首批在两轮分别需要 27.309、101.310 秒。

共享方案必须等待前批完成。第二轮第 2、3 批的首段有效译文分别在整篇开始约 109.61、207.23 秒后出现，不能将逐批的 8 秒解释为任务开始后 8 秒即可阅读所有后续页。第一轮对应约 30.30、51.15 秒。

initialize 为约 0.05–0.09 秒；实际 thread/start 为约 0.08–0.23 秒。创建 thread 本身没有解释几十至几百秒的总耗时差异。RPC 计时包含请求发送至响应到达，并不是服务端内部剖析。

## 结论与验证

当前分支已验证的收益是后续请求更快开始输出，以及实际历史前缀缓存复用。完整文档的总耗时改进没有稳定复现；第一轮更快，第二轮明显更慢。保留用户要求的单 thread 设计，本次只扩展测试入口与保存测量记录，没有改动生产翻译行为。

`go test ./internal/reader -run 'TestTranslation|TestLiveTranslationThreadSpeed' -count=1` 通过（普通运行跳过真实测试）；两轮显式开启的真实测试均通过，合计 180 段记录全部通过结构与原文覆盖校验。这里的 180 是两轮×两组×45 段，语义翻译质量未人工验证。

重跑命令（仓库根目录下先进入 `apps/server`）：

```sh
READER_TEST_TRANSLATION_SPEED=1 \
READER_TRANSLATION_SPEED_PARAGRAPHS=15 \
READER_TRANSLATION_SPEED_OUTPUT=/tmp/reader-full-batch-speed.json \
go test ./internal/reader -run '^TestLiveTranslationThreadSpeed$' -count=1 -v -timeout=25m
```

增加 `READER_TRANSLATION_SPEED_REVERSE=1` 可反转执行顺序。不设置样本大小参数时仍使用原有每批两段小样本。
