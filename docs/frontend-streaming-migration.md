# 前端实施方案：迁移 LobeHub 流式输出

日期：2026-10-05。执行对象：Reader 前端。状态：待实施的交付要求，不代表迁移已经完成。

任务派给新建的 `Reader 流式迁移 · 前端` 会话，使用独立 worktree，不占用正在处理其他工作的 `Build frontend` 会话。执行 F1–F4，不止停留在调研或预览。组件 API、状态管理、文件拆分和调度细节可由前端按测试证据决定；第 3 节及共同契约的冻结项不可自行更改。记录实现选择与验证结果即可，不需要对每个内部设计逐次请示。

配套文档：[后端统一服务与适配器](./backend-streaming-adapter.md)。当前线上格式的唯一对接依据是 [Agent 流式输出约定](./agent-streaming-contract.md)。上游机制和固定版本证据见 [LobeHub 源码调查](./research/lobehub-streaming-upstream.md)。

## 1. 目标与当前基线

最终将 Reader 的 AI 回答迁移到 LobeHub 同款流式 Markdown 引擎，完成 Markdown、代码高亮、公式、滚动和动态效果接入。保留 React、Vite、shadcn/Base UI、Go 本地服务、PDF/EPUB 阅读引擎和原文引用。

按四个可独立验收的阶段推进：先验证 Markdown 组件，再验证滚动，再验证动态效果，最后接入真实对话并完成迁移。前三阶段使用固定事件回放，不依赖 Agent 登录和生成速度；第四阶段必须使用真实后端联调。

代码基线为 `2afe113`。三种 Agent 的真实增量协议接入已合入后端；前端仍在 `Workspace.tsx` 内维护临时字符串，以普通 div 显示，并随回答更新调用 `scrollIntoView`。备用 API 当前可能一次返回完整答案。旧调研文档中针对更早提交的“Codex 只在消息完成后输出”“图片主路径缓冲全文”不再适用于该基线。

## 2. 组件选择与边界

采用 **`@lobehub/streamdown`**，先以已调研的 `1.4.0` 为验证基线并锁定实际依赖版本。它不是 Vercel 的 `streamdown`。LobeHub 应用的完整聊天模块不作为迁移单位。

同款底层提供流式尾部修复、分块解析、缓存与动态呈现。代码高亮、数学公式、复制按钮和 Reader 的主题需要上层组件接入。可参考 Lobe UI 的 MIT 实现选择性移植，保留版权及来源；交互控件仍使用现有 Base UI。不能把底层包安装成功当作迁移完成。

建议职责如下，文件名可随现有结构调整，但职责边界应保持：

| 位置 | 职责 |
| --- | --- |
| `apps/web/src/chat/AssistantPanel.tsx` | 对话与请求状态，隔离阅读器主体的高频更新。 |
| `apps/web/src/chat/MessageMarkdown.tsx` | 对历史和生成中回答提供统一渲染入口，封装 Markdown、公式、高亮和样式。 |
| `apps/web/src/chat/useChatStream.ts` | 消费统一事件、维护原文、请求身份、终态和保存同步。 |
| `apps/web/src/chat/useChatScroll.ts` | 贴底跟随、用户上滚、回到底部、内容高度变化。 |
| `packages/api-client/src/index.ts` 及相邻模块 | POST SSE 传输、增量 UTF-8 解码、分帧、错误与取消；无 Agent 原始协议。 |
| `packages/ui/src/components/scroll-area.tsx` | 按需暴露真实 Viewport 的 ref/事件，不替换现有 primitive。 |

`MessageMarkdown` 的输入应接近 `{ content, generating, reducedMotion }`，不接受 `codex`、`claude`、`kimi` 的原始事件或 API Key。`SourceReferences` 继续单独使用可信的 PDF/EPUB 位置；不要从模型生成的 Markdown 链接推导文档位置。

## 3. 前后端契约

继续使用 `POST /api/documents/{documentId}/chat` 和现有会话认证。协议具体字段以 [对接约定第 1–3 节](./agent-streaming-contract.md#1-请求接口) 为准。本阶段不另创一套 SSE 名称；以下只是 SDK 解码后的联合类型，与现有线上事件对应。

共同契约新增的“本轮联调冻结项”是最终规范。`provider` 仍为请求必填字段；本轮不新增 connectionId、响应序号、消息 ID 或新终态。前端按这份固定格式独立制作 fixtures，后端也用相同形状测试。内部连接抽象不影响请求格式。

```ts
type ChatStreamEvent =
  | { event: "status"; data: { status: "reading" | "reading-image" } }
  | { event: "delta"; data: { text: string } }
  | { event: "fallback"; data: { message: string } }
  | { event: "error"; data: { error: string } }
  | { event: "done"; data: { ok: true } };
```

SDK 可以保留旧 `onDelta` 接口并增加统一 `onEvent` 消费接口，最终由一处解析和校验产生上述事件。不要在多个 UI 组件重复分帧。传输需要覆盖 UTF-8 跨字节分片、事件跨网络块、一块含多个事件、CRLF、多行 data、注释/空行和不合法 JSON。正文换行使用 JSON 转义，不以网络读取块作为正文边界。

目前没有服务端序号、message ID 或断点续传。前端用本地递增请求标识和 `documentId` 绑定回调，切书或新请求后拒绝旧回调；不凭空假设服务端支持恢复，不自动重新 POST。未知事件不得追加为正文，终态后不得继续追加；不兼容的必需协议变更须先协调后端。

## 4. F1：单独验证 Markdown

建立开发用组件预览入口及确定性事件回放器，接收固定文本、分片和时间安排。该入口不读取书库、不调用真实模型，不进入正式产品导航。记录启动命令和实际预览地址，供人工检查。

固定样本至少包含中文长段落、中英混排、emoji/组合字符、标题、嵌套列表、引用、窄表格、行内代码、多语言代码围栏、行内与块级公式、脚注和引用式链接。用逐字、按词、随机确定性分片和全文一次到达四种方式回放，包含在 Markdown 定界符中间切断的情况。

流式和历史消息必须走同一入口。对上游已知的跨块脚注、引用式链接限制，选定并记录一种实现：提供能解析全局定义的适配，或生成结束后统一按全文静态渲染。后一种方案必须检查内容、链接与滚动位置，避免完成时可见跳变。不能悄悄丢掉定义或宣称已支持。

Markdown 原文、已展示文本与渲染器临时语法修复结果必须分开。复制回答复制收到的原文；复制代码复制代码正文；不得保存为显示补齐的反引号、括号或公式结束符。历史原文以数据库为准。

代码高亮优先评估 Lobe UI 的 Shiki 增量方案；高亮与公式依赖按需加载，公式字体/CSS 随应用提供，离线可用。普通 Markdown 正文不继承 `white-space: pre-wrap`；代码、表格和长公式在自身区域溢出，不能撑宽最小 250px 的侧栏。

初期关闭 raw HTML 和可执行预览；外部图片不自动加载。对链接协议设允许范围，桌面外链沿用或新增受控打开流程，不能假定 `target="_blank"` 在 Electron 中可用。不得借此开放任意 IPC、文件路径或命令执行。

**完成标准：** 所有样本在分片与全文模式下最终可读内容一致；未完成语法不导致组件异常；代码、表格、公式与深浅主题可人工检查；脚注策略和限制有记录。此阶段暂不启用流式字符动画。

## 5. F2：单独验证滚动

在真实 Base UI ScrollArea Viewport 上维护“跟随末尾”与“用户正在阅读历史”两种状态。以实际滚动容器为准，不对整个页面调用 `scrollIntoView`。

回答开始时允许进入跟随；只有仍跟随时，内容新增或高度变化才调整到底部。用户向上滚动后立即暂停跟随，后续 delta、公式排版、高亮完成和侧栏缩放均不能把用户拉回末尾。提供 Base UI 的“回到底部”按钮恢复跟随。

监听内容高度变化，处理字体加载、公式、高亮及窗口大小变化。正确区分程序滚动与用户滚动，避免自己触发的滚动事件误判意图。贴底阈值以 Reader 侧栏实测选定，不直接照搬 LobeHub 的 300px。

**完成标准：** 长回答生成中可稳定上翻、选择和复制；回到底部后恢复跟随；完成消息替换、失败提示和图片附件不会拖动阅读器主体；侧栏展开/收起后位置合理。先用无动态效果的固定回放验收。

## 6. F3：单独验证动态效果与性能

启用同款引擎的平滑和新增文字淡入，测量实际展示尾延迟。只设一个负责视觉节奏的层；本地 hook 可以合并状态提交，但不再叠加独立逐字队列或 LobeHub 应用的 300ms 传输缓冲。

系统 reduced motion 开启时禁用字符/块淡入和平滑补放，数据合并可保留。不能仅依赖上游已有 CSS，因为调研版本没有覆盖全部字符动画。历史消息不重新播放；替换原文、切文档和回看旧消息不应重播整段。

收到 `done`、`error` 或主动停止后，立即终止延迟动画并显示已经接收的原文，不丢尾字、不继续慢速补放。模型已经生成完成不应因前端动画继续显示“生成中”。代码高亮不得反复让旧 token 淡入。后台标签页恢复后先追齐内容，不回放积压动画。

用固定的 10KB、100KB 和接近当前 1MiB 输出上限的原文回放，记录 React 提交次数/耗时、主线程长任务、内存与结束后的展示延迟。选定同一机器与回放参数，比较 F1 无动画基线和 F3。报告生产入口及异步 chunk 增量。数值是实测结果，不预先编造性能提升比例。

**完成标准：** 动态效果可以关闭；流式更新不会造成历史消息全量动画重播；长输出有有界补放策略；取消/完成不丢字；未发现持续增长的回调、Observer 或内存占用。性能问题须修复或明确限制后再进入正式替换。

## 7. F4：接入实际对话并完成迁移

移出 `Workspace` 的高频对话状态，正式替换普通文本回答，历史助手消息也使用新的 Markdown 入口。模型选择等现有交互可保留，渲染器不按 Agent 分支。兼容多个小 delta 和备用 API 返回的一个大 delta。

| 输入/动作 | 必须行为 |
| --- | --- |
| `status` | 进入等待状态，状态文字不混入回答。 |
| `delta` | 立即累计原文并交给渲染层；不等完整答案。 |
| `fallback` | 单独显示切换提示；现契约只在尚未输出正文时切换。 |
| `done` | 原文立即追齐，停止生成；读取 `api.messages` 并以数据库记录替换临时回答，不追加最终全文。 |
| done 后消息查询失败 | 保留当前原文，显示同步待重试；不能把已确认保存的答案清空。 |
| `error` | 停止生成，保留已收到部分供查看/复制，标为未完成，不显示成成功保存。 |
| 主动取消 | 立即 abort 和停止动画；不等待取消事件。保留部分文本，之后用消息列表核对保存竞态。 |
| 无 done 的 EOF/断网/解析错误 | 显示完成状态未确认，读取消息列表核对；不自动重发生成请求。 |
| 切换文档/卸载 | 中止请求、清理调度与观察器；旧 finally/查询响应也不得更新新文档。 |

临时消息到数据库消息的替换应保持稳定布局。目前服务端不返回消息 ID，不能用“找到一条内容相同的消息”认定是本次结果；结合请求开始前的消息 ID 集合、本次文档和单请求约束核对。无法确定时保留待同步状态，后续明确的请求/消息身份扩展由双方共同修改契约。

真实联调覆盖 Codex、Claude、Kimi 的文字和图片能力；缺少登录环境时记录阻塞，不能用模拟测试代替真实成功。后台 PDF 沉淀任务不因前端渲染迁移改变其产物。

## 8. 文件所有权、交付与验收

前端负责 `apps/web` 的聊天模块、相关 `packages/ui`、API client 的传输消费和前端测试。后端负责 Go、OpenAPI schema 与生成的 API 类型；需要修改共享生成文件时先按后端契约合并，不手工改 `schema.d.ts`。现有工作区有其他会话修改，实施前核对分支与 diff，不回退无关变更。

前端拥有本次渲染依赖及 `pnpm-lock.yaml` 的修改权。后端不得并发改 SDK 传输、UI 或锁文件。共同契约冻结内容由协调会话维护；如发现必须更改的接口问题，先报告具体原因和兼容方案，继续独立可做的阶段，不能双方各自改一版。

最小自动测试覆盖：分片解码、不完整 Markdown 最终一致性、终态去重、失败保留部分、取消清理、旧请求隔离和完成同步失败。滚动状态逻辑可单测，但 JSDOM 通过不等于真实布局正确。执行 `pnpm typecheck`、`pnpm test`、`pnpm build`，记录结果。

视觉验收遵守项目规则：提供可访问预览和明确人工步骤，不使用浏览器自动化作视觉验收。逐项记录 F1、F2、F3、F4 的完成/待确认状态及限制。只有正式聊天已接入、自动检查通过、人工检查结果明确，才能交付“迁移完成”；独立预览页只算阶段验证。

向协调会话报告每阶段结果、当前分支/提交、修改文件、测试和预览命令。F4 前确认后端已交付相同契约的可运行版本；无需等待后端完成才开始 F1–F3。若另一个任务正在修改同一文件，先保留其改动并划清范围，不用 reset/整体覆盖解决冲突。

阶段记录写入自己拥有的 `docs/implementation/frontend-streaming-progress.md`。任务分支以已提交 main 加本轮任务文档为基线，不复制其他会话仍在编辑的未提交产品代码；最终集成前再核对 main 的新变更。提交仅包含自己拥有的改动，先交付分支与证据，由协调会话统一安排联调和集成，不自行覆盖主工作区或合并 main。
